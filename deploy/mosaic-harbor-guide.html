The MosAIc Harbor

How three apps got a home in the cloud

Three apps needed somewhere that runs them day and night, restarts them if they crash, and never mixes up their stuff with anyone else's. Here's everything we used to build that, explained the simple way.

Docker — the magic lunchbox

Code by itself isn't enough to run — it needs the right tools around it, like a recipe needing the right pans. Docker packs an app plus everything it needs into one sealed box called an image. Open that box on any computer, anywhere, and it works exactly the same way every time. (That's why Docker's mascot is a whale carrying containers on its back.)

docker build = pack the lunchbox docker run = open it an opened box = a "container"

ECR — Amazon's warehouse shelf

Once a lunchbox is packed, it needs somewhere everyone can find a copy later. Amazon runs a giant warehouse called ECR (Elastic Container Registry). We put our lunchbox recipes on its shelves — one shelf per app — so that any computer in Amazon's harbor can grab one whenever it needs to.

ECR = the shelfdocker push = put a copy on the shelf

Kubernetes — the harbor master

Someone still has to go get those lunchboxes, put them on ships, keep watch, and make a fresh one the moment any falls overboard. That's Kubernetes' whole job — its name literally means "helmsman," the person who steers a ship, which is why its badge is a ship's wheel.

Node = one real ship (computer) Pod = a small crate holding one opened lunchbox Deployment = "always keep N crates afloat somewhere"

If a ship needs maintenance, the harbor master quietly moves its crates to another ship. We never have to watch for that ourselves.

EKS — a ready-made harbor, rented

We didn't build a harbor from scratch. Amazon rents us a whole one, already built, with ships and a harbor master on staff — that's EKS (Elastic Kubernetes Service). We just show up with cargo and orders.

Namespaces — our own labeled dock

The harbor is shared. Another team already runs a large operation on it, under a dock called "mosaic," and it has nothing to do with our apps. So our apps live in their own clearly labeled zones: mosaic-ai for the real thing, and mosaic-ai-nonprod for a test copy of the chat app. Each is kept apart from everyone else's crates.

Habit to keep: because the harbor is shared, every command names its dock (-n mosaic-ai). Never rely on a default, and never change anything in a namespace that is not ours.

Services — a signpost that never loses track

Crates move around the harbor sometimes. So how does one crate find another? Every app gets a Service — a signpost with one fixed name that always points to wherever that app's crates currently are, even after they move.

worldmonitor's app talks to its redis-rest crate by name, not by chasing it around the docks.

Storage trunks — so nothing forgets

Some crates need to remember things — a database remembering every chat, for instance. If Kubernetes ever swaps a crate for a fresh one, a plain crate forgets everything overnight! So we strap on a waterproof trunk (a Persistent Volume) that stays behind and gets reattached to the new crate, memories intact.

A real example: a brand-new trunk has a stray folder called lost+found sitting in it. That is normal, but a database's first-time setup refuses to start in a folder that is not empty, so it has to be pointed at a clean sub-folder inside.

Notes & locked notes — ConfigMaps and Secrets

Every app needs settings (like which color theme to use) and passwords. Settings go on an open note anyone nearby can read — a ConfigMap. Passwords go in a locked note — a Secret — that only the right crates are allowed to open.

Helm — the whole order, written as one recipe

Writing out every crate, signpost, and trunk by hand, one instruction at a time, would take forever and be easy to get wrong. So each app's whole order gets written down once, in a Helm chart — a recipe book. One command reads the book and sets everything up at once. Want to change something? Edit the recipe, run it again.

helm installhelm upgrade

The front gate — shared, and run by the platform team

Inside the harbor, crates talk to each other freely. Visitors from the internet come through one shared front gate that the platform team runs: a load balancer (ALB) plus a gateway. To open a door for an app, we add a small route (an HTTPRoute) that says "requests for this hostname go to that Service." Today only mosaic-ai-chat has doors, at prod.ai.mosaicinsurance.com and nonprod.ai.mosaicinsurance.com. worldmonitor and common-service stay internal-only on purpose until we decide who should reach them.

Where it landed

Three apps, each packed into lunchboxes on Amazon's shelf, with one recipe book per app describing every crate, signpost, trunk, and note it needs. All of it lives on Amazon's rented harbor, inside our own mosaic-ai dock, watched around the clock by the harbor master, who restarts anything that falls overboard whether or not anyone is looking.

Delivery

Release process

The same seven steps apply to every application. Details and commands are in the workbook tab.

  1. Build the image from a clean working tree and tag it with the date and commit, for example 20261002-3f9a1c2.
  2. Push to ECR and confirm the image digest.
  3. Set the tag in the environment's Helm values file and run helm lint.
  4. Deploy to nonprod with helm upgrade --atomic --timeout 5m. A release that fails its readiness checks is rolled back automatically.
  5. Verify: rollout status, pod readiness, /health, /api/config, logs, and one user journey.
  6. Promote the same tag to prod with the same command, then verify again.
  7. Record the Helm revision and image digest in the release log.

Current practice. Releases are run by hand from one workstation. mosaic-ai-chat and worldmonitor still run :latest tags; a baseline version tag now exists for mosaic-ai-chat so that rollback is possible, and the workbook requires unique tags from the next release. The environment-specific Helm values files are not in version control.

What actually changed from the EC2 way

Before: one server, reached by SSH, updated by hand. Here's exactly what that turned into, and the direct mapping between the old way of thinking and the new one.

Before

One ship, no captain

One EC2 instance was the whole operation. To update it: SSH in, git pull, then repack the lunchboxes by hand — docker compose up -d --build for one app, scripts/upgrade.sh for another, a different ritual for each. If a container fell over, Docker might quietly restart it — but only as long as the box itself stayed up. If the box itself had a bad day, everything on it went down until a person noticed.

After

A fleet, with a harbor master watching

There isn't one ship anymore — there's a whole fleet (dozens of real computers, shared with other teams), watched around the clock by Kubernetes. Updating any app is the same command shape every time: helm upgrade --install. If a container falls over, a new one appears within seconds. If an entire machine dies, that app's pods quietly move to a different one — nobody has to notice, let alone SSH in.

The direct mapping

One correction worth making up front: a Pod is not the new EC2 instance. That's a Node. A Pod maps to what one of your containers already was.

Before (EC2)After (Kubernetes)What actually changed
The EC2 instance — the whole server→ Node You had one. Now there are many, pooled together as one fleet.
One container / one docker-compose service→ Pod This is the real match for what you used to run — not the EC2 box.
docker-compose.yml→ Helm chart Same idea — describe every piece — now able to describe a fleet-wide setup, not one box.
docker compose up -d --build / scripts/upgrade.sh→ helm upgrade --install Same purpose, now one command shape for every app instead of three separate habits.
.env file sitting on disk→ Secret / ConfigMap Same idea, now an access-controlled object instead of a plaintext file anyone on the box can read.
Compose's container-name networking→ Service Same idea — call things by name — now works across the whole fleet and survives things moving.
Hand-configured nginx→ HTTPRoute on the shared gateway Same job, the front door, now declared as a small YAML route on a gateway the platform team runs, instead of edited files on a box.
restart: unless-stopped→ Kubernetes restarting + rescheduling pods The old one only helped if the box itself stayed alive. This one survives the box dying too.

The pros

✓

Self-healing beyond anything Compose could do — survives an entire server dying, not just a container crashing.

✓

One deploy command, every app — instead of three different upgrade habits that had grown apart over time.

✓

A real rollback — helm rollback reverts everything a release touched (config, replica count, secret wiring), not just code the way git checkout did.

✓

Room to grow — add more machines to the fleet, or tell one app to run more copies, without redesigning anything.

✓

The chart is the whole truth, checked into git — not "whatever's currently configured on the box," half-remembered by whoever set it up.

Worth knowing — this isn't free: more moving parts to learn; the fleet costs money even sitting idle, unlike one EC2 box that was just a box; and some things are not built yet. Only mosaic-ai-chat is reachable from the internet so far, there is no automated build pipeline (docker build → push → helm upgrade are still run by hand), and nothing auto-scales.

✓

Browse & inspect — live lists across one or many clusters that update over a websocket, no refresh button. Click into anything for a plain-English summary (a crashing pod's banner says why, in one sentence, not just the raw CrashLoopBackOff), the full YAML in a real VS Code editor, and a map of what it's connected to.

✓

Maintenance workbook · namespaces mosaic-ai and mosaic-ai-nonprod

New code no longer arrives by git pull on a server. You build an image, push it to ECR under a new tag, and tell Helm to run that tag. Kubernetes then pulls the image from ECR itself. This workbook covers doing that safely, undoing it, and keeping everything else healthy. Commands are PowerShell, run from your workstation; the kubectl and helm lines also work unchanged in a Linux shell.

commit→ docker build→ push to ECR, new tag→ edit tag in values file→ helm upgrade nonprod→ verify→ helm upgrade prod→ verify + log

Boundaries. This workbook covers only the mosaic-ai (prod) and mosaic-ai-nonprod namespaces. The mosaic, envoy-gateway-system and kube-system namespaces belong to other teams: look, never change.

Section 3

Standard upgrade

One procedure for all three services. Steps run in order because each depends on the one before.

A

Log in to ECR

Needed once per 12 hours. The registry address is used by every later step.

$env:AWS_PROFILE = "mosaic"
$REG = "481781217475.dkr.ecr.eu-west-1.amazonaws.com"
aws ecr get-login-password --region eu-west-1 | docker login --username AWS --password-stdin $REG

Seen on a managed Windows laptop with Docker Desktop: docker login fails with 400 Bad Request: invalid argument. The same token is accepted when sent directly, so the fault is in docker login itself. Write the token into Docker's config instead. Docker Desktop may restore credsStore after a restart, so rerun this if pushes start failing with an authentication error.

fallback: write the token into ~/.docker/config.json (tested 2 Oct 2026)

$token = aws ecr get-login-password --region eu-west-1
$auth  = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("AWS:$token"))
$cfgPath = "$env:USERPROFILE\.docker\config.json"
$cfg = Get-Content $cfgPath -Raw | ConvertFrom-Json
if (-not $cfg.auths) { $cfg | Add-Member -NotePropertyName auths -NotePropertyValue ([pscustomobject]@{}) }
$cfg.auths | Add-Member -NotePropertyName $REG -NotePropertyValue ([pscustomobject]@{auth=$auth}) -Force
$cfg.PSObject.Properties.Remove('credsStore')
[IO.File]::WriteAllText($cfgPath, ($cfg | ConvertTo-Json -Depth 10), (New-Object Text.UTF8Encoding $false))

check that it worked: prints a JSON manifest

docker manifest inspect "$REG/mosaic-common-service:0.3.0"
B

Choose a new, unique image tag

Every release gets a tag that has never been used. The date plus the git commit works well.

git status --short      # must print nothing
$TAG = "$(Get-Date -Format yyyyMMdd)-$(git rev-parse --short HEAD)"
$TAG                    # for example 20261002-3f9a1c2

Why not :latest. Three facts, all checked on the live cluster on 2 Oct 2026: the ECR repositories are mutable, every deployment uses imagePullPolicy: IfNotPresent, and mosaic-ai-chat and worldmonitor currently run :latest. Together that means:

1. A new push to :latest changes nothing in Helm's eyes, because the tag text is identical, and nodes that already cached the old image never pull the new one.

2. The push overwrites :latest, so the previous image is gone. There is nothing to roll back to.

Rule: a tag is used once and never reused. Only mosaic-common-service already follows this (0.3.0).

C

Build and push

Build only the images you changed. Run the block for your service from its repository root.

mosaic-ai-chat

docker build -f Dockerfile.k8s -t "$REG/mosaic-ai-chat:$TAG" .
docker push "$REG/mosaic-ai-chat:$TAG"

worldmonitor (three images; build and push whichever changed)

docker build -f Dockerfile -t "$REG/worldmonitor:$TAG" .
docker build -f Dockerfile.relay -t "$REG/worldmonitor-ais-relay:$TAG" .
docker build -f docker/Dockerfile.redis-rest -t "$REG/worldmonitor-redis-rest:$TAG" docker
docker push "$REG/worldmonitor:$TAG"
docker push "$REG/worldmonitor-ais-relay:$TAG"
docker push "$REG/worldmonitor-redis-rest:$TAG"

mosaic-common-service

docker build -t "$REG/mosaic-common-service:$TAG" .
docker push "$REG/mosaic-common-service:$TAG"

confirm the tag is in ECR (repeat for each repository you pushed)

aws ecr describe-images --repository-name mosaic-ai-chat --image-ids imageTag=$TAG --region eu-west-1 --query "imageDetails[0].imageDigest" --output text

mosaic-ai-chat is the heavy build because it compiles the whole LibreChat client. Allow several minutes.

D

Put the new tag in the values file

Edit the file, then check the chart still renders. Start with the nonprod file for mosaic-ai-chat; the other two services have no nonprod copy and go straight to values-prod.yaml.

deploy/helm/mosaic-ai-chat/values-nonprod.yaml

api:
  image:
    tag: "20261002-3f9a1c2"
helm lint deploy/helm/mosaic-ai-chat -f deploy/helm/mosaic-ai-chat/values-nonprod.yaml

Edit the file. Do not use --set for the image tag. A tag set on the command line is not saved anywhere. The next time you run helm upgrade for an unrelated config change, Helm applies the older tag from the file and quietly downgrades the app.

E

Deploy to nonprod and verify

Chat only. --atomic waits for the pods to become ready and rolls back by itself if they do not, so a failed release does not stay broken.

helm -n mosaic-ai-nonprod upgrade --install mosaic-ai-chat deploy/helm/mosaic-ai-chat -f deploy/helm/mosaic-ai-chat/values.yaml -f deploy/helm/mosaic-ai-chat/values-nonprod.yaml --atomic --timeout 5m --history-max 20

Now run every check in section 7 against https://nonprod.ai.mosaicinsurance.com. Do not continue until they pass. Worldmonitor and common-service have no nonprod copy, so for those the safety net is --atomic and the rollback target from section 4.

F

Promote the same tag to prod

Edit the tag in the matching values-prod.yaml to the exact tag that passed nonprod, then run the command for your service.

# mosaic-ai-chat  (repo: mosaic-ai-chat)
helm -n mosaic-ai upgrade --install mosaic-ai-chat deploy/helm/mosaic-ai-chat -f deploy/helm/mosaic-ai-chat/values.yaml -f deploy/helm/mosaic-ai-chat/values-prod.yaml --atomic --timeout 5m --history-max 20

# worldmonitor  (repo: worldmonitor_aidan_mosaic)
helm -n mosaic-ai upgrade --install worldmonitor deploy/helm/worldmonitor -f deploy/helm/worldmonitor/values.yaml -f deploy/helm/worldmonitor/values-prod.yaml --atomic --timeout 5m --history-max 20

# mosaic-common-service  (repo: mosaic_common_service)
helm -n mosaic-ai upgrade --install mosaic-common-service deploy/helm/mosaic-common-service -f deploy/helm/mosaic-common-service/values.yaml -f deploy/helm/mosaic-common-service/values-prod.yaml --atomic --timeout 5m --history-max 20

Run section 7 again against prod. If any check fails within ten minutes of the change, roll back first (section 4) and investigate afterwards.

G

Record it

One line in the release log (section 10) per deployment. Without it, the next person cannot tell what is running or what to return to.

helm -n mosaic-ai history mosaic-ai-chat --max 3
kubectl -n mosaic-ai get deploy mosaic-ai-chat-api -o jsonpath="{.spec.template.spec.containers[0].image}"

Section 4

Rollback and downgrade

Decide quickly, act once, investigate afterwards. Prefer Helm for every undo so the cluster and Helm's records stay in agreement.

SituationActionCommand
The release failed while --atomic was running Nothing to do. Helm already reverted. Confirm the pods are healthy. helm -n mosaic-ai history <release> shows a line starting "Rollback to".
The new image is bad and the previous one has a version tag preferred Downgrade by tag: put the previous tag back in the values file and run the same upgrade command as step E or F. Edit tag:, then helm -n mosaic-ai upgrade ... --atomic. Works for any tag still in ECR.
A values-file change broke something (config, replicas, routes) Roll the release back to the last good revision. helm -n mosaic-ai rollback mosaic-ai-chat <REVISION> --wait --timeout 5m
The release has to stop right now Scale the workload to zero, then fix properly. Set it back afterwards, because Helm will not know you changed it. kubectl -n mosaic-ai scale deploy/mosaic-ai-chat-api --replicas=0
A Secret was edited wrongly Kubernetes keeps no history of Secrets, so restore from the copy you took before editing (section 6). kubectl apply -f secrets-backup.yaml, then restart the deployment.

Where helm rollback stops. It restores only what the release created. It does not undo database contents, volume data, or the four objects that were created by hand outside Helm: mosaic-ai-chat-secrets, mosaic-ai-chat-certs, mosaic-ai-chat-librechat-config and worldmonitor-secrets. And if the earlier revision used :latest, rolling back re-applies the same tag and the running image does not change.

Do not roll mosaic-ai-chat back past revision 9 in prod or revision 3 in nonprod. Those revisions moved the uploads and help-cache volumes to EFS, and Kubernetes will not let a claim change back to a single-attach disk in place. Downgrade by image tag instead.

Avoid kubectl rollout undo for Helm-managed workloads. It works, but afterwards the cluster differs from what Helm recorded.

One-time: give every image a rollback target

Today the live images exist only under :latest. Before the first versioned release, add a second tag to the exact image that is running. This copies a reference, not the image, takes seconds, and changes nothing the cluster uses. Do it before the next push to :latest, because that push is what replaces the image. Tested on mosaic-ai-chat on 2 Oct 2026: the new tag and latest point at the same digest.

$env:AWS_PROFILE = "mosaic"
$stamp = Get-Date -Format yyyyMMdd
foreach ($repo in "mosaic-ai-chat","worldmonitor","worldmonitor-ais-relay","worldmonitor-redis-rest") {
  $img = aws ecr batch-get-image --repository-name $repo --region eu-west-1 --image-ids imageTag=latest --accepted-media-types "application/vnd.oci.image.index.v1+json" "application/vnd.docker.distribution.manifest.list.v2+json" "application/vnd.oci.image.manifest.v1+json" "application/vnd.docker.distribution.manifest.v2+json" --query "images[0]" --output json | ConvertFrom-Json
  $f = "$env:TEMP\$repo-manifest.json"
  [IO.File]::WriteAllText($f, $img.imageManifest, (New-Object Text.UTF8Encoding $false))
  aws ecr put-image --repository-name $repo --region eu-west-1 --image-tag "baseline-$stamp" --image-manifest "file://$f" --image-manifest-media-type $img.imageManifestMediaType --query "image.imageId.imageTag" --output text
  Remove-Item $f
}

mosaic-ai-chat already has baseline-20261002, created from the image running in prod that day (digest sha256:90ee2030…). Run the loop for the three worldmonitor repositories before their next release. mosaic-common-service needs nothing: 0.3.0 is already a version tag.

Section 5

Data services and backups

MongoDB (chats, users), Postgres with pgvector (document embeddings) and Meilisearch (search index) run inside the cluster on EBS volumes. This deployment sets up no scheduled backup for any of them, and rolling an app back does not roll its data back.

Never bump the mongo, pgvector or meilisearch image tag in a routine release. A MongoDB major version changes its feature-compatibility level, a Postgres major version cannot open the old data directory, and Meilisearch versions need an export and re-import. Treat each as its own change: back up, rehearse on nonprod, then do prod.

·

Back up before any data-affecting change

Tested on 2 Oct 2026 against the nonprod databases: dump, copy to your workstation, clean up. Swap the namespace to mosaic-ai for prod. The tar: Removing leading '/' message is harmless.

Rehearse this on nonprod before you need it in anger. A backup that has never been restored is a hope, not a backup.

Moving a volume to a different storage class

Done for the chat api's uploads and interactive-help-cache volumes on 2 Oct 2026 (single-attach EBS to shared EFS, class efs-sc), so the api can use the RollingUpdate strategy. A claim's storage class and access mode cannot be edited, so the claim is deleted and recreated. This causes one outage of a few minutes. Rehearse on nonprod first; it took about four minutes there.

$ns = "mosaic-ai-nonprod"     # then repeat with mosaic-ai
$pod = kubectl -n $ns get pod -l app.kubernetes.io/component=api -o jsonpath="{.items[0].metadata.name}"

# 1. copy the data out (here the help cache; uploads were empty)
kubectl cp "${ns}/${pod}:/app/api/data/interactive-help-cache" ".\help-cache-backup"

# 2. stop the api so the claims are released, then delete the two claims
kubectl -n $ns scale deploy/mosaic-ai-chat-api --replicas=0
kubectl -n $ns wait --for=delete pod -l app.kubernetes.io/component=api --timeout=120s
kubectl -n $ns delete pvc mosaic-ai-chat-uploads mosaic-ai-chat-interactive-help-cache

# 3. with the new class and ReadWriteMany in the values file, Helm recreates them
helm -n $ns upgrade --install mosaic-ai-chat deploy/helm/mosaic-ai-chat -f deploy/helm/mosaic-ai-chat/values.yaml -f deploy/helm/mosaic-ai-chat/values-nonprod.yaml --atomic --timeout 5m

# 4. the pod has a new name now; look it up again, then copy the data back folder by folder
$pod = kubectl -n $ns get pod -l app.kubernetes.io/component=api -o jsonpath="{.items[0].metadata.name}"
Get-ChildItem .\help-cache-backup -Directory | ForEach-Object {
  kubectl cp $_.FullName "${ns}/${pod}:/app/api/data/interactive-help-cache/$($_.Name)"
}

values file keys that make it work (prod and nonprod)

api:
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}
  uploads:
    persistence: {storageClassName: efs-sc, accessMode: ReadWriteMany}
  interactiveHelp:
    cache:
      persistence: {storageClassName: efs-sc, accessMode: ReadWriteMany}

efs-sc is the platform team's class on their shared EFS filesystem (it maps every file to uid 1000, which works for this app). Keep databases off it.

Section 8

Troubleshooting

Every row here happened during this build, so the cause and fix are known rather than guessed.

SymptomUsual causeCheck and fix
Pod shows ImagePullBackOff or ErrImagePull The tag was mistyped or never pushed. kubectl -n mosaic-ai describe pod <pod> (read Events), then aws ecr describe-images --repository-name <repo> --image-ids imageTag=<tag>. Fix the tag and upgrade.
Pushed new code, nothing changed The tag is the same text as before. Helm sees no difference and nodes reuse their cached image. Use a new tag for every release (step B). A restart alone can reuse the cached copy too.
CrashLoopBackOff A missing environment key, an unreachable dependency, or a probe that fires too early. kubectl -n mosaic-ai logs <pod> --previous and kubectl -n mosaic-ai get events --sort-by=.lastTimestamp. Seen before: MongoDB listening only on localhost (fixed with --bind_ip_all) and probes with too short a delay (now 30 s).
Pod stuck in ContainerCreating, volume attach error The volume can attach to one node at a time and the old pod still holds it. This is why mongodb, vectordb and meilisearch use Recreate: wait for the old pod to terminate. The chat api no longer has this problem because its volumes are on EFS. If a Recreate pod stays stuck, look at kubectl describe pod Events before deleting anything.
Postgres refuses to start: directory not empty A new EBS volume contains a lost+found folder. The chart sets PGDATA to a sub-folder to avoid it. Keep that setting if a volume is ever recreated.
Config change has no effect Pods were not restarted. kubectl -n mosaic-ai rollout restart deployment/<name>, then check with printenv.
SSO button missing from the login page ALLOW_SOCIAL_LOGIN is false. The SAML button is hidden behind it. Set api.config.allowSocialLogin: "true", upgrade, restart. Confirm socialLoginEnabled in /api/config.
SSO error AADSTS700016 The host's Entity ID is not registered in the Entra ID Enterprise App. First confirm the pod has the right SAML_ISSUER with printenv. If it does, the Microsoft team must add the Identifier and Reply URL.
Browser says "Not secure" on the bare domain The shared load balancer's certificate covers only *.prod.ai... subdomains. The infra team must attach the ACM certificate for the bare host as an extra certificate on the listener.
"Unable to locate credentials", or kubectl cannot authenticate The mosaic AWS profile is missing, or the access key was rotated. aws sts get-caller-identity --profile mosaic. Re-run aws configure --profile mosaic.

Section 10

Housekeeping, ownership and the release log

The things that are easy to forget until they hurt.

✓

Keep copies of the values files. values-prod.yaml and values-nonprod.yaml are ignored by git, so today they exist only on the machine used to deploy. Store a copy in a private, access-controlled place. They hold no passwords, but they are the only record of how prod is configured.

✓

Lock the registry down once versioned tags are in use. Until then, making a repository immutable would block pushes to :latest. Do not run this before section 4's baseline step.

aws ecr put-image-tag-mutability --repository-name mosaic-ai-chat --image-tag-mutability IMMUTABLE --region eu-west-1
aws ecr put-image-scanning-configuration --repository-name mosaic-ai-chat --image-scanning-configuration scanOnPush=true --region eu-west-1
✓

Rotate the AWS access key on a schedule. Kubectl, Helm, Docker and Kubus all depend on it. Create the new key, run aws configure --profile mosaic, confirm with kubectl get nodes, then delete the old key.

✓

Diary dates. SAML signing certificate expires 16 April 2029. Set a reminder for March 2029 to confirm Microsoft has a replacement ready.
